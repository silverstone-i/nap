# Database provisioning

The specification's [Database provisioning](../specs/nap-platform-specification.md#database-provisioning)
contract owns the lifecycle. [ADR 0014](../ADRs/0014-register-cell-provisioning.md) records the page workflow; ADR 0013 records the baseline replacement.

## Preparation

Install PostgreSQL 18 tooling and OpenSSL. Copy `apps/api/.env.example` to `.env`
and provide the selected environment's real settings. Never use placeholder passwords.
Runtime uses NODE_ENV; every operator command requires `--env dev|test|prod`.

Local setup uses `SETUP_DATABASE_DEV` or `SETUP_DATABASE_TEST`, a credential-free
endpoint such as `localhost:5432/postgres`. The script combines it with `nap_admin`
and the selected `NAP_ADMIN_PSWD_DEV/TEST`. That existing login creates databases
and roles and runs migrations, with LOGIN, CREATEDB and CREATEROLE privileges.
`nap_app` receives minimal runtime grants; setup rejects elevated privileges,
role memberships, and object ownership for that runtime role. No third local login
is required. See the specification's [Environment configuration](../specs/nap-platform-specification.md#environment-configuration).
Existing passwords and unrelated database owners are never changed by setup.

Keep `.env` synchronized with `.env.example` in variable names, order and comments;
only configured values differ. Preserve real values when updating the inventory.

Private state defaults to `apps/api/.env.provisioning.<env>.json`, with mode 0600.
It records generated passwords, infrastructure IDs, endpoints, and operation identity.
Back it up securely: DEV provisioning and the remaining admin CLI use it to resume.
It must never enter Git. PROD cell recovery state lives in Render secrets. `NAP_PROVISION_STATE` and `NAP_ENV_FILE` override the default paths.
A lock directory prevents simultaneous writers to one state file. After a crashed
process, locks with a recorded dead process ID are reclaimed. Older locks without
ownership metadata require verification that no command is running before removal.
Do not discard state to retry a failed operation.

DEV/TEST passwords come from their shared role settings when supplied. Missing
passwords are independently generated by `openssl rand -hex 32` and saved before
creation. Existing credentials are validated, never rotated. Admin DEV setup publishes
the resulting admin endpoint and shared passwords locally; TEST fixtures manage their
own configuration. Supplied PROD component passwords are preserved in private state.

## Prepare admin before any cells

```bash
npm run db:setup:admin -- --env dev
npm run db:migrate:admin -- --env dev
npm run db:bootstrap -- --env dev
```

This creates `nap_dev_admin`, applies the five baseline migrations and the cell-workflow forward migration, then creates root
identity/tenant/membership and platform policy. No cell is required. Bootstrap replay
preserves the password; recovery alone uses `--reset-root-password`.

The consolidated baseline applies only to empty databases. Historical migration
ledgers are refused and must not be manually erased to bypass the check. Database
renaming, resets, and transition from a populated environment are outside this flow.

## Prepare first and subsequent cells

Open Management → Cells → Register cell. Enter a suffix such as east or 1;
the server previews nap_dev_cell_east (DEV) or nap_prod_cell_east (PROD).
Submission creates a disabled UUID and runs creation, migration, reference seeding,
configuration persistence, live loading and activation. Watch progress in the list;
closing the page does not cancel work. Retry resumes a failed operation by UUID.
Activate rechecks readiness; Disable prevents assigned tenant access.

The table shows copyable UUID, database name, status and actions. Cell code and
editable display-name fields are removed. No manual API restart or operator cookie
is needed. The four cell CLI commands are removed. Admin CLI remains unchanged.

TEST fixtures call the same provisioning service directly with isolated TEST
credentials and nap_test_cell_<suffix> databases. The management endpoint rejects
TEST; fixture configuration never writes the developer's .env or calls Render.

## Production on Render

Local PROD admin setup, migration and bootstrap read five nonsecret defaults from the repository's
`render.yaml`: `RENDER_WORKSPACE_ID`, `RENDER_REGION`, `RENDER_POSTGRES_VERSION`,
`RENDER_POSTGRES_PLAN` and `RENDER_DISK_GB`. Nonblank shell values take precedence
over nonblank private `.env` values, then Blueprint defaults. Blank placeholders
fall through. `NAP_ENV_FILE` remains supported. Supply `RENDER_API_KEY` and
`RENDER_API_SERVICE_ID` privately. Complete explicit settings work without a
Blueprint; otherwise it must contain one web service and unique literal settings.
Setup validates configuration before opening state or contacting Render. Errors
identify saved state when progress was persisted; existing state is preserved for
retry. This fallback applies only to local PROD admin maintenance. Each operation discovers the direct operator IPv4 through OpenDNS and temporarily allows its /32, preserving existing rules. Cleanup removes only the saved operation-owned rule; retries recover interrupted cleanup. External TLS uses verify-full. Successful migration and bootstrap publish the internal admin connection and merge admin recovery state into Render service secrets without deploying or overwriting cell entries.

Configure the API service with RENDER_API_KEY, workspace, region, PostgreSQL
version, plan, disk size and service ID. Register cell chooses PROD from the server
environment. It creates an independently hosted database through Render, preserves
resource identity on retry, and uses the internal connection from the running API.
Credentials and private recovery state are saved in service environment variables,
including NAP_PROVISION_STATE_PROD. Activation never triggers a deployment.
Startup retrieves the latest saved connection maps for process-restart recovery.
Maintenance credentials remain on the server and never enter browser responses.

## Recovery and testing

Choose Retry for the same UUID using the existing credentials and saved state. Completed resources remain. Central progress distinguishes registered,
created, migrated, seeded, and enabled. Private state also records infrastructure
request progress; failures carry credential-free diagnostics.

An uncertain Render create is reconciled against the saved operation-specific user.
If no matching resource is visible, retry reconciliation later rather than issuing a
second create. An uncertain local CREATE DATABASE without its operation comment and
without its confirmed creation result requires operator inspection before resuming. Do not
reset intent flags without verifying the provider/database outcome. No deployment
is part of cell activation.

Tests own test-data seeding and disposable resources. Run `npm test` with the required
PostgreSQL tools installed; production Render behavior is mocked. Real DEV/PROD
execution, paid resource creation, and deployments require separately authorized runs.

## Upgrade existing registrations

Apply `npm run db:migrate:admin -- --env dev` before starting this version of the API
(use the corresponding environment for other installations). Migration
`006-cell-workflow` takes database names from saved provisioning metadata and
preserves UUIDs, assignments, availability and physical databases. It refuses the
transition if a registration has no verified mapping; reconcile that metadata with
the physical identity before retrying. Editable old labels are never a source.
Unfinished operations appear in Cells and can be retried with their original private
state. Keep that state until recovery is complete.

## Complete greenfield operator bootstrap

Run admin setup, migration and bootstrap, then start the API and web application. Sign in as root and register a cell in Tenant Management → Cells. The first successfully provisioned available cell automatically hosts the operator tenant. Tenant Management → Tenants displays bootstrap progress, cell availability, projection and RBAC readiness. Root remains an identity without an employee record.

A bootstrap failure leaves the cell available. Use Retry bootstrap on the operator tenant to resume the saved operation and cell. Restart resumes interrupted work. Do not create another root or rerun initial setup to recover cell synchronization. Normal bootstrap reruns preserve existing records and completed state; upgrades never enroll existing installations. Explicit root password recovery remains a separate operation.

Tenant Management also contains Portal users, Platform access, Access and Audit. Each destination retains its permission requirements; controlled access requires a reason. Legacy control URLs redirect into this navigation.

Apply the additive admin migration before running this version of the API. It creates bootstrap tracking without enrolling existing installations. Deploy the matching administration client and reload legacy open control pages; manual reconcile requests are retired. Existing customer contracts remain unchanged.

## Clean development environment

Stop the API before running `npm run db:clean:dev -- --confirm`. This destructive
command uses `SETUP_DATABASE_DEV` (which must target the `postgres` maintenance
database) and `NAP_ADMIN_PSWD_DEV`. It removes `nap_dev_admin` and all databases
matching `nap_dev_cell_<suffix>` on that server, including partially provisioned
cells. Every matching database must be owned by `nap_admin`; an ownership mismatch
stops cleanup before any drops. Other database names and PostgreSQL roles remain.
Do not share these DEV database names with another installation on the same server.

After the drops succeed, it sets `CELL_DATABASES_DEV='{}'` in `apps/api/.env` and
removes `apps/api/.env.provisioning.dev.json`. Other environment values remain.
The standard `NAP_ENV_FILE` and `NAP_PROVISION_STATE` overrides are supported for
isolated fixtures; unset an inherited nonempty `CELL_DATABASES_DEV` before use.
The command takes the provisioning-state lock. Stop the API so its in-memory
connections and configuration cannot race with cleanup.

Drops are not transactional. If cleanup fails partway, saved state remains until
the final configuration write succeeds; correct the cause and rerun the same
command. Missing databases/state are harmless on rerun. Then follow
[Prepare admin before any cells](#prepare-admin-before-any-cells) and
[Greenfield operator bootstrap](#complete-greenfield-operator-bootstrap).
