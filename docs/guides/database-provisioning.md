# Database provisioning

The specification's [Database provisioning](../specs/nap-platform-specification.md#database-provisioning)
contract owns the lifecycle. ADR 0013 records the baseline replacement decision.

## Preparation

Install PostgreSQL 18 tooling and OpenSSL. Copy `apps/api/.env.example` to `.env`
and provide the selected environment's real settings. Never use placeholder passwords.
Runtime uses NODE_ENV; every operator command requires `--env dev|test|prod`.

Local setup requires `INFRA_DATABASE_URL_DEV` or `INFRA_DATABASE_URL_TEST`, pointing
to a maintenance database such as `postgres` with an infrastructure login capable
of creating databases and roles. That login must be separate from restricted
`nap_admin` and `nap_app`. Existing incompatible roles cause refusal; the scripts
never reset passwords, change an unrelated database's owner, or drop a database.

Private state defaults to `apps/api/.env.provisioning.<env>.json`, with mode 0600.
It records generated passwords, infrastructure IDs, endpoints, and operation identity.
Back it up securely: it is needed to resume and must never enter Git or the runtime
service. `NAP_PROVISION_STATE` and `NAP_ENV_FILE` override the default paths.
A lock directory prevents simultaneous writers to one state file. After a crashed
process, verify no process is running before manually removing its `.lock` directory.
Do not discard state to retry a failed operation.

DEV/TEST passwords come from their shared role settings when supplied. Missing
passwords are independently generated by `openssl rand -hex 32` and saved before
creation. Existing credentials are validated, never rotated. Admin DEV setup publishes
the resulting admin endpoint and shared passwords locally; TEST fixtures manage their
own configuration. Supplied PROD component passwords are preserved in private state.

## Prepare admin before any cells

```bash
npm run db:setup:admin -- --env dev
npm run db:migrate:admin -- --env dev
npm run db:bootstrap -- --env dev
```

This creates `nap_dev_admin`, applies five frozen admin migrations, then creates root
identity/tenant/membership and platform policy. No cell is required. Bootstrap replay
preserves the password; recovery alone uses `--reset-root-password`.

The consolidated baseline applies only to empty databases. Historical migration
ledgers are refused and must not be manually erased to bypass the check. Database
renaming, resets, and transition from a populated environment are outside this flow.

## Prepare first and subsequent cells

```bash
npm run db:setup:cell -- --env dev --cell-name east
npm run db:migrate:cell -- --env dev --cell-id <returned-uuid>
npm run db:seed:cell -- --env dev --cell-id <returned-uuid>
npm run db:activate:cell -- --env dev --cell-id <returned-uuid>
```

The supplied suffix determines `nap_dev_cell_east`; use `asia`, `1`, or another
unique lowercase letter/digit/underscore suffix. There is no sequence allocation.
Setup returns the registered UUID. Subsequent commands use that UUID, never a list's
first entry. Repeat the same sequence with another suffix for another cell.

Registration is disabled until activation. Central provisioning metadata and a
protected `cell.physical_identity` record bind the UUID, environment, database name,
and operation UUID. Setup creates that identity before application migrations.
Cell seeding inserts the committed countries/currencies snapshot without replacing
existing values. No tenant, tenant role, or root identity is created by cell seeding.

Activation requires `API_ORIGIN_DEV` and an authenticated operator cookie supplied
as `OPERATOR_COOKIE_DEV` through private environment configuration. It adds the UUID
entry to `.env`, preserving unrelated entries. Restart the API after that update and
rerun activation if the first attempt reports it is not ready. Activation calls the
permission-checked cell-readiness endpoint on the running API and enables the cell
only when that exact identity and reference seed are verified. A failed attempt
retains the disabled registration. Configure the API using the same shared passwords
saved during setup, including generated passwords if no values were supplied.

Assign tenants through the existing control-plane workflow after activation.
Provisioning a tenant supplies its tenant-scoped RBAC roles; the root identity remains
central. Preparing a cell does not automatically assign the root tenant.

## Production on Render

Use `--env prod` with the same commands. Supply `RENDER_API_KEY`, workspace ID,
region, PostgreSQL version, plan, disk size, and API service ID from the example.
No paid plan is selected automatically. The API service must be in the intended
workspace/region. `API_ORIGIN_PROD` must be HTTPS; supply `OPERATOR_COOKIE_PROD`
privately for activation. Local maintenance connectivity must be permitted by Render's
external access policy; external connections use TLS.

Setup calls Render's [create Postgres API](https://api-docs.render.com/reference/create-postgres)
with both resource and database names (`nap_prod_admin`, `nap_prod_cell_east`). Each
gets an independent instance. An operation-specific infrastructure username permits
reconciliation of a lost create response without adopting an unrelated resource.
The scripts save IDs and wait for availability before configuring the fixed roles.
No schemas are migrated during setup.

After admin migration/bootstrap, supply the API's runtime-only admin connection and
other normal application secrets for its initial deployment. Cell activation publishes
the selected cell connection and runtime admin entry through the
[environment-variable API](https://api-docs.render.com/reference/update-env-var), then
triggers and waits for deployment. It preserves other cell entries while removing
maintenance passwords from the runtime cell map. Service-owned variables are used;
ensure linked environment groups do not conflict. Infrastructure and maintenance
secrets are not published. No application service is created by these scripts.

## Recovery and testing

Repeat the failed command using the same environment, state file, suffix/UUID, and
credentials. Completed resources remain. Central progress distinguishes registered,
created, migrated, seeded, and enabled. Private state also records infrastructure
request/deployment progress; failures carry a fixed code, never driver diagnostics.

An uncertain Render create is reconciled against the saved operation-specific user.
If no matching resource is visible, retry reconciliation later rather than issuing a
second create. An uncertain local CREATE DATABASE without its operation comment or
an uncertain deployment response requires operator inspection before resuming; the
script refuses automatic adoption or another request. Do not reset intent flags
without verifying the provider/database outcome. A known failed deployment can be
retried after correction; a pending deployment resumes its saved ID.

Tests own test-data seeding and disposable resources. Run `npm test` with the required
PostgreSQL tools installed; production Render behavior is mocked. Real DEV/PROD
execution, paid resource creation, and deployments require separately authorized runs.
