# PRD 0004 — Authentication and session management

- **Status:** Approved
- **Date:** 2026-08-07
- **Related:** [ADR-0004](../ADRs/0004-portal-user-login-and-tenant-selection.md),
  [ADR-0012](../ADRs/0012-rbac-caching-and-staleness.md),

## Overview

Authentication is a component of the Auth module. It defines how a
portal user proves who they are, what a session is, how long it lives,
and how it ends. Its tables and router are owned by the `auth` code
module, except the session-policy columns, which live on
`admin.tenants` (owned by the `tenants` code module).

Every other component depends on it: role-based access control (RBAC,
[PRD 0003](0003-role-based-access-control.md)) authorizes a user this
component has authenticated, and continuous persistence
([PRD 0005](0005-data-persistence.md)) assumes sessions can end
without warning and lose nothing. The architecture is recorded in ADRs
0004, 0014, and 0015.

## Users and scenarios

- **Employee** — logs in with email and password, lands in their one
  tenant, works all day, and is logged out by the absolute lifetime,
  not by idle timeouts, because they keep working.
- **Client contact** — logs in occasionally, walks away mid-session,
  and is idle-logged-out with a warning first.
- **Vendor contact** — one login, several tenants; sees the tenant
  picker at login and switches tenants without re-authenticating
  (ADR-0004).
- **Tenant admin (Administrator)** — sets the tenant's idle-window
  bounds and absolute session lifetime.
- **Any portal user** — picks their own idle window within the
  admin's bounds, changes their password, and logs out.

## Data tables

All tables live in the `admin` schema. Standard audit columns are
omitted throughout; `admin.sessions.created_at` (an audit column) is
load-bearing as the absolute-lifetime anchor (ADR-0014).

### admin.portal_users

Global login identity, one row per person, keyed on email
(ADR-0004). Existing table; this PRD adds `session_idle_minutes`.

| Column               | Type         | Notes                                                        |
| -------------------- | ------------ | ------------------------------------------------------------ |
| id                   | uuid         | Primary key.                                                 |
| email                | varchar(128) | Unique among active rows.                                    |
| password_hash        | text         | argon2id (ADR-0015). NULL = no credential; login refused.    |
| user_type            | varchar(16)  | `employee` \| `client` \| `vendor_contact`.                  |
| status               | varchar(20)  | Default `invited`. Only `active` may log in.                 |
| session_idle_minutes | integer      | New. 30 \| 60 \| 90 \| 120, default 30; clamped per session. |

### admin.portal_user_tenants

Existing table, unchanged; defined by ADR-0004 and listed here because
login reads it: the binding rows resolve the landing tenant
(`MAX(last_used_at)` over bindings in active tenants) and produce the
tenant-picker list.

### admin.sessions

New. One row per live session (ADR-0014).

| Column          | Type        | Notes                                                   |
| --------------- | ----------- | ------------------------------------------------------- |
| id              | uuid        | Primary key.                                            |
| portal_user_id  | uuid        | FK to admin.portal_users, cascade on delete.            |
| token_hash      | text        | Hash of the current refresh token. Unique. Rotates.     |
| idle_expires_at | timestamptz | Sliding idle expiry; advanced by each accepted refresh. |
| revoked_at      | timestamptz | NULL while live; set by logout or rotation-reuse theft. |

### admin.tenants (session-policy columns)

Existing table (`tenants` code module); this PRD adds three columns.

| Column                   | Type    | Notes                                  |
| ------------------------ | ------- | -------------------------------------- |
| session_idle_min_minutes | integer | Lower idle-window bound. Default 30.   |
| session_idle_max_minutes | integer | Upper idle-window bound. Default 120.  |
| session_absolute_hours   | integer | Absolute session lifetime. Default 12. |

## API

The auth router is not a standard resource router: no route in it is
generated by the standard-route factory, none demands a permission
cell, and the mutating-verb-to-level mapping of
[RULES/api-standard-routes.md](../RULES/api-standard-routes.md) does
not apply. Login and refresh are unauthenticated by nature; the rest
require a valid access token but no RBAC grant — a session's owner
may always manage that session.

| Method | Path                       | Description                                                                                                                          |
| ------ | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| POST   | /api/auth/v1/login         | Verify email + password, create the session, set both cookies, return the binding list and expiry pair (ADR-0004, ADR-0014).         |
| POST   | /api/auth/v1/refresh       | Rotate the refresh token, reissue the access token, slide the idle expiry, return the expiry pair. Refused past the absolute expiry. |
| POST   | /api/auth/v1/logout        | Revoke the session and clear both cookies.                                                                                           |
| POST   | /api/auth/v1/switch-tenant | Validate the tenant code against the caller's active bindings and update the stored active tenant (ADR-0004).                        |
| PUT    | /api/auth/v1/password      | Change the caller's password; requires the current password; revokes the caller's other sessions.                                    |
| PUT    | /api/auth/v1/idle-window   | Set the caller's `session_idle_minutes` to one of the four values.                                                                   |

## Business rules

### Credentials

- Login verifies the password with argon2id and rehashes when the
  stored parameters lag configuration (ADR-0015).
- A NULL `password_hash`, an unknown email, and a wrong password all
  produce the same refusal response — no user enumeration.
- Only a portal user with status `active` may log in.
- A password change requires the current password and revokes every
  other session belonging to that user.

### Session lifecycle

- Login issues an access JSON Web Token (JWT) carrying `sub` + `ph`
  (15-minute lifetime) and an opaque refresh token, both as httpOnly
  cookies, backed by one `admin.sessions` row (ADR-0014).
- Each refresh rotates the refresh token; presenting an
  already-rotated token revokes the session (ADR-0014).
- The idle expiry slides forward by the user's effective idle window
  on each accepted refresh; a refresh after `idle_expires_at` is
  refused.
- A refresh is refused once the session's age exceeds the effective
  absolute lifetime, regardless of activity.
- A revoked or expired session refuses refresh; the access token
  lapses within its 15-minute lifetime and the user must log in again.

### Session policy

- The effective idle window is the user's `session_idle_minutes`
  clamped between the tenant's `session_idle_min_minutes` and
  `session_idle_max_minutes`; the effective absolute lifetime is the
  tenant's `session_absolute_hours`.
- For a user with several active bindings, the effective policy is
  the most restrictive across those bindings' tenants; a tenant
  switch never changes it mid-session (ADR-0014).
- Only the tenant admin edits the tenant policy columns; only the
  user edits their own idle window.

### Activity and warning

- Activity is client input — keyboard, pointer, touch. The client
  requests a refresh only when input occurred since the last refresh;
  application programming interface (API) traffic, autosave included,
  never counts (ADR-0014, ADR-0016).
- Login and refresh responses carry `idle_expires_at` and
  `absolute_expires_at`; the client warns the user 5 minutes before
  `idle_expires_at` and offers to continue. Accepting the warning is
  input and triggers a refresh; ignoring it lets the session end.

## Open questions

- Password reset — self-service reset needs outbound email the
  platform does not have yet; until then, resets are administrative.
- Multi-factor authentication (MFA) — not designed; the token and
  session model does not preclude it.
- Login throttling and lockout — some brake on repeated failures is
  needed; mechanism and thresholds undecided.
- Single sign-on (SSO) — undecided; would sit beside password login,
  not replace the session model.
- Session inventory — whether a user can list and remotely revoke
  their other sessions ("log out other devices") beyond the
  password-change revocation.

## Out of scope

Authorization — every permission question
([PRD 0003](0003-role-based-access-control.md)); cross-tenant access
for NAP staff and impersonation (the platform-administration PRD);
per-tenant module entitlement (the licensing PRD); permission-cache
staleness and `X-Token-Stale`
([ADR-0012](../ADRs/0012-rbac-caching-and-staleness.md) — this PRD
reuses the flow, RBAC owns it).

## Success criteria

- A login with an unknown email, a wrong password, or a NULL
  `password_hash` returns the identical refusal; a correct login sets
  two httpOnly cookies and returns the binding list and expiry pair.
- A user whose status is not `active` cannot log in with a correct
  password.
- A refresh with the current token succeeds and invalidates the prior
  token; replaying the prior token revokes the session and the next
  refresh with the current token is refused.
- With no client input, no refresh is sent and the session refuses
  refresh after the idle window; continuous autosave traffic alone
  never extends a session.
- A refresh after the absolute lifetime is refused even when input is
  continuous.
- A user's chosen idle window outside the tenant bounds is clamped:
  the effective expiry moves by the bound, not the choice.
- For a vendor contact in two tenants with different policies, the
  tighter policy governs, before and after a tenant switch.
- A password change revokes the user's other sessions: their next
  refresh is refused.
- Logout revokes the session and clears both cookies; a subsequent
  refresh with the old token is refused.
- The warning appears 5 minutes before idle expiry; accepting it
  extends the session, ignoring it ends the session on schedule.
